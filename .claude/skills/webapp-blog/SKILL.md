# webapp-blog

이 스킬은 my-blog 프로젝트(마크다운 블로그 + 미니 웹앱 포트폴리오)에서 새 웹앱을 추가할 때 쓰는 고정된 4단계 파이프라인이다. 각 단계는 별도 서브에이전트(Agent 도구)에게 위임하고, 단계 사이에 반드시 사용자 승인을 받는다.

## 절대 규칙

- **승인 없이 구현을 시작하지 않는다.** Plan 단계 결과(spec.md)를 사용자가 승인하기 전에는 Build 서브에이전트를 절대 실행하지 않는다.
- **Build와 Review는 반드시 다른 서브에이전트**로 분리한다. 같은 에이전트가 자기 코드를 검증하지 않는다.
- 각 웹앱은 `/apps/{앱이름}/` 폴더 안에서 자체 완결된다. 블로그의 다른 파일(`posts/`, `static/`, `build.js`, 다른 `/apps/*/`)은 건드리지 않는다.
- 막히면(모호한 요구사항, 승인 대기, 반복 실패 등) 즉시 사용자에게 알리고 멈춘다. 임의로 범위를 넓히거나 다음 단계로 넘어가지 않는다.

## 웹앱 자체 규칙 (Build/Review 서브에이전트에게 전달)

- 순수 HTML, CSS, JavaScript만 사용 (React/Vue 등 프레임워크·빌드 도구 금지 — 프로젝트 전체 원칙과 동일)
- 외부 라이브러리 사용 최소화. CDN 스크립트/스타일 로드는 허용.
- 모바일에서도 정상 동작해야 한다 (반응형 레이아웃, 터치 대응).
- 폴더 안에서 완결: 앱이 참조하는 HTML/CSS/JS/에셋은 모두 `/apps/{앱이름}/` 안에 둔다.

## 파이프라인

사용자가 웹앱 주제를 주면 아래 순서를 그대로 따른다. 앱 이름(`{앱이름}`)은 주제를 kebab-case로 슬러그화해서 정한다.

### 1단계 — Plan

1. `apps/{앱이름}/` 아래에서 작업한다는 전제로, Plan 서브에이전트에게 전달할 지침 파일 `apps/{앱이름}/.plan-instructions.md`를 작성한다. 지침 파일에는 다음을 포함한다:
   - 사용자가 요청한 웹앱 주제와 요구사항 원문
   - 위의 "웹앱 자체 규칙" 전체
   - 산출물: `apps/{앱이름}/spec.md` 하나만 작성할 것. 코드는 아직 작성하지 않을 것.
   - spec.md에 포함할 항목: 어떤 웹앱인지 한두 문단 요약, 핵심 기능 목록, 파일 구조(`/apps/{앱이름}/` 하위 트리), 사용할 CDN 라이브러리(있다면), 모바일 대응 방식
2. Agent 도구로 서브에이전트를 실행해 이 지침 파일을 프롬프트로 전달하고 `apps/{앱이름}/spec.md`를 작성하게 한다. (subagent_type: 코드 설계이므로 `Plan` 에이전트 사용, 없으면 `general-purpose`)
3. 완료되면 spec.md 내용을 사용자에게 요약해서 보여주고 승인을 요청한다. **승인 전에는 절대 2단계로 넘어가지 않는다.**

### 2단계 — Build

1. 승인을 받으면, Build 서브에이전트에게 전달할 지침 파일 `apps/{앱이름}/.build-instructions.md`를 작성한다. 포함 내용:
   - `apps/{앱이름}/spec.md` 경로와 "이 spec.md를 그대로 구현할 것"이라는 지시
   - 위의 "웹앱 자체 규칙" 전체
   - 수정 가능 범위: `apps/{앱이름}/` 안의 파일만. 그 외 어떤 파일도 만들거나 수정하지 말 것을 명시.
   - 산출물: 실제로 동작하는 HTML/CSS/JS 파일 일체
2. Agent 도구(subagent_type: `general-purpose`, 코드 작성이 필요하므로)로 실행해 지침 파일을 프롬프트로 전달하고 구현을 맡긴다.

### 3단계 — Review

1. Build 완료 후, **Build와 다른 새 서브에이전트**에게 전달할 지침 파일 `apps/{앱이름}/.review-instructions.md`를 작성한다. 포함 내용:
   - `apps/{앱이름}/spec.md`와 실제 구현이 일치하는지 확인할 것
   - 브라우저(Chrome 자동화 도구)로 실제 열어서 핵심 기능과 모바일 뷰포트를 직접 테스트할 것
   - 코드 상의 명백한 버그, 프레임워크/빌드 도구 사용 여부, `/apps/{앱이름}/` 바깥 파일 수정 여부를 점검할 것
   - 산출물: `apps/{앱이름}/review.md` — 통과 여부, 발견한 문제, 수정이 필요하면 무엇을 고쳤는지 기록
   - 문제를 발견하면 해당 서브에이전트가 `apps/{앱이름}/` 범위 안에서 직접 수정까지 하도록 지시
2. Agent 도구(subagent_type: `general-purpose` 또는 `Explore`+수정 필요하므로 `general-purpose`)로 실행.
3. review.md에 남은 미해결 문제가 있으면 사용자에게 보고하고 다음 단계로 넘어가지 않는다.

### 4단계 — Embed

Review를 통과하면 직접(서브에이전트 없이) 다음을 수행한다:

1. 블로그 메인 페이지(`index.html` — `dist/index.html`이 아니라 빌드 전 소스 템플릿이 따로 있다면 그쪽; my-blog는 `build.js`가 `dist/index.html`을 생성하므로, 포트폴리오 카드 목록은 `build.js`가 `/apps/`를 스캔해 카드를 생성하도록 하거나, 정적 카드 마크업을 유지보수하는 지점을 확인한 뒤 그 소스를 수정한다)에 웹앱 카드를 추가한다. 카드에는 제목, 짧은 설명, 미리보기 이미지 또는 `<iframe>` 링크(`apps/{앱이름}/index.html`)를 넣는다.
2. 모바일/데스크톱, 라이트/다크 모드에서 카드가 깨지지 않는지 직접 확인한다.
3. `git add`로 `apps/{앱이름}/` 관련 파일과 카드가 추가된 파일만 스테이징하고(지침 파일 `.plan-instructions.md`/`.build-instructions.md`/`.review-instructions.md`는 커밋에서 제외 — 일회성 작업 지시서이므로), 커밋한다. 커밋 메시지는 어떤 웹앱을 추가했는지 명확히 담는다.
4. 커밋 후 사용자에게 완료를 보고한다. (push는 사용자가 별도로 요청할 때만 진행)

## 폴더 구조 참고

```
my-blog/
  CLAUDE.md
  build.js, lib/, static/, posts/     # 블로그 본체 (건드리지 않음)
  apps/
    {앱이름-1}/
      spec.md                         # Plan 산출물
      review.md                       # Review 산출물
      index.html, style.css, script.js, ...  # Build 산출물
    {앱이름-2}/
      ...
```

## 서브에이전트에게 넘길 때 체크리스트

- [ ] 전용 지침 파일(`.plan-instructions.md` / `.build-instructions.md` / `.review-instructions.md`)을 먼저 작성했는가
- [ ] 지침 파일에 수정 가능 범위(`/apps/{앱이름}/`만)를 명시했는가
- [ ] Build와 Review를 서로 다른 서브에이전트 호출로 분리했는가
- [ ] Plan 승인 없이 Build를 시작하지 않았는가
